Context:
S2-50 auth/session boundary runtime is merged. App.Desktop has auth/session boundaries, an HTTP client for the existing backend sign-in endpoint, disabled local token persistence, and tests for redaction/session behavior.

S2-51 SignIn runtime enablement is merged. App.Desktop can show the SignIn surface, accept user-entered credentials, call the existing control-plane sign-in endpoint, and update in-memory session state when credentials are valid.

Manual smoke after S2-51 showed that App.Desktop can reach the SignIn flow, but the operator cannot sign in because no account/password was provisioned. First run also does not offer user registration.

That gap must not be solved by adding open desktop self-registration. Identity creation must remain server-controlled.

User smoke finding:
- App.Desktop SignIn surface can be shown.
- App.Desktop can be configured to use a control-plane API base address.
- The operator has no provisioned account/password for sign-in.
- First run has no registration flow.
- The next approved runtime work must create or document a safe account/bootstrap path before further manual SignIn smoke can be meaningful.

Current auth/bootstrap observations:
- App.Desktop posts credentials only to the existing App.Api `/api/auth/sign-in` endpoint through `HttpDesktopAuthClient`.
- `DesktopSignInService` rejects missing credentials, avoids raw exception leakage, and updates only `IDesktopSessionState` after successful auth.
- `DesktopAuthOptions` accepts a safe absolute HTTP/HTTPS control-plane base address and rejects user-info, query, fragment, or non-root paths.
- `App.Api` maps `/api/auth/sign-in` to `IAuthService.SignInAsync` and writes authentication audit entries for sign-in success/failure.
- `Modules.Auth` owns password verification, opaque access/refresh token creation, session persistence, and role/permission mapping.
- `DevelopmentAuthBootstrapService` exists only for Development environment and feature-flagged development bootstrap. It is not an approved production/operator bootstrap path.
- `tools/App.Maintenance` already has operator-style account upsert patterns for integration and incident-routing accounts. Those commands read passwords from operator environment variables and do not accept command-line password arguments.
