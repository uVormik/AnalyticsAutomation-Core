Selected technology:
WPF standalone desktop shell + BlazorWebView / App.UI.Shared RCL reuse where useful.

Decision:
Primary desktop client implementation may proceed in a future task using a standalone WPF desktop shell.

BlazorWebView is allowed only as an embedded native desktop UI composition mechanism for selected App.UI.Shared Razor components where useful.

App.Web / Browser / PWA are not primary desktop.

Primary executable:
The primary desktop client must be a standalone WPF desktop application. App.Desktop-style naming is allowed, but actual project creation remains a later implementation task.

BlazorWebView boundary:
- BlazorWebView may host selected App.UI.Shared Razor components inside the native WPF desktop shell where useful.
- BlazorWebView must not be used to turn App.Web into the primary desktop client.
- Browser/PWA/App.Web must not become the primary desktop client through a shell wrapper.

WPF shell responsibilities:
- Windowing.
- Native file picker.
- Native desktop lifecycle.
- Secure token/session storage boundary.
- Hosting upload orchestration services.
- Hosting BlazorWebView where useful.

Upload/service boundaries:
- Upload orchestration, hashing, precheck, direct-site adapter, and upload receipt should live in testable services where possible.
- Video bytes must not go through App.Api.
- Server remains the control plane.
- Runtime implementation must preserve:
  SignIn -> GroupTree -> file select -> SHA-256 -> businessObjectKey -> PreUploadCheck -> direct site upload boundary -> UploadReceipt

Not selected:
- .NET MAUI Desktop as first option.
- Pure WPF-only as mandatory direction.
- Pure WinUI 3 as default.
- Avalonia.
- Uno Platform.
- Electron/Tauri as default.
- Browser/PWA/App.Web as primary desktop.

Rationale:
- Windows-first practicality.
- Standalone executable.
- Local file picker and large video handling.
- SHA-256 on local bytes.
- Direct client -> site upload boundary.
- Secure token/session storage via native desktop boundary.
- Lower operational risk for the first upload slice.
- Controlled App.UI.Shared reuse without returning to Browser/PWA/App.Web as primary.

Consequences:
- Runtime implementation can create a new desktop-client task after this PR merges.
- Runtime implementation must remain scoped and cannot change API/contracts/migrations/workflows/deploy without separate approval.
- WebView2/runtime prerequisite, packaging/update story, and test strategy must be explicitly handled in the implementation task.

Risks:
- Misuse of BlazorWebView as App.Web-in-a-shell.
- Duplicated UI patterns.
- Unclear packaging/update policy.
- WebView2 runtime prerequisite.
- Secure storage design still needs implementation details.

Mitigations:
- WPF shell responsibilities are narrow.
- Upload orchestration and adapters are testable services.
- App.Web is not referenced as the primary desktop surface.
- Implementation task must include packaging/update/security/test plan.

Revisit criteria:
- If Windows-first is no longer sufficient.
- If App.UI.Shared reuse through BlazorWebView proves unmaintainable.
- If packaging/update or WebView2 prerequisite is unacceptable.
- If owner explicitly changes desktop platform scope.

Rollback:
Revert this decision PR before runtime implementation, or create a superseding decision PR after implementation begins.
