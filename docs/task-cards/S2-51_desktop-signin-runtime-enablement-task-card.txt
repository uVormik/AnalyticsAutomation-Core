Current S2-50 auth/session foundation observed:
- IDesktopAuthClient and HttpDesktopAuthClient exist for POST /api/auth/sign-in.
- DesktopSignInRequest, DesktopAuthResult, DesktopAuthStatus, and DesktopAuthError avoid exposing credentials through diagnostics.
- IDesktopSessionState and DesktopSessionState support signed-out, signed-in, load, set signed-in, and sign-out transitions.
- IDesktopSessionStore exists, but the registered DisabledDesktopSessionStore deliberately does not persist tokens.
- DesktopSessionSnapshot exposes only safe session metadata and token-presence booleans.
- DesktopCompositionRoot currently registers UnavailableDesktopAuthClient by default.
- Desktop auth/session tests cover redaction, disabled persistence, session transitions, and composition registration.

Future S2-51 runtime scope:
- Add a narrow App.Desktop auth options/config boundary for the App.Api base address.
- Keep credentials out-of-band and user-entered; do not put credentials in config examples or repo files.
- Enable minimal SignIn UI/view-model/component wiring inside App.Desktop only.
- Use the existing IDesktopAuthClient / HttpDesktopAuthClient only against the already existing backend sign-in endpoint.
- Wire HttpDesktopAuthClient through the App.Desktop composition root only when an API base address is configured safely.
- Preserve safe default behavior when the API base address is missing or invalid; SignIn must stay unavailable or clearly disabled without leaking secrets.
- On successful SignIn, update the existing in-memory IDesktopSessionState through SetSignedInAsync.
- Keep DisabledDesktopSessionStore behavior unless a separate approved task explicitly adds real Windows secure storage.
- Add focused App.Desktop unit tests for options/config, composition-root behavior, SignIn success/failure wiring, session update, redaction, and safe default behavior.
- Keep the runtime slice online-only and auth-only.

Security guardrails:
- No hardcoded credentials.
- No token, password, or Authorization logging.
- No raw exception message in UI-safe errors if it may contain secrets.
- No raw response body in UI-safe errors if it may contain secrets.
- No plaintext token persistence.
- No secrets in config examples.
- API base address may be configured, but credentials must remain out-of-band/user-entered.
- Default runtime behavior must stay safe if API base address is not configured.
- Passwords must not be copied into long-lived state beyond the sign-in attempt.
- UI/log/test diagnostics must use safe result codes/messages and redaction assertions.

Contracts:
No shared contract changes are allowed in this docs-only PR or in the future S2-51 runtime PR.

The future S2-51 runtime may use only the already existing backend sign-in endpoint shape that S2-50 HttpDesktopAuthClient targets. If the existing endpoint is unavailable, incompatible, or requires contract/server changes, the future runtime PR must stop and report the blocker instead of inventing a new contract.

Migrations:
No migrations are allowed.

The future S2-51 runtime must not require database schema changes.

Feature flags:
No feature flags are added in this docs-only PR.

The future runtime should prefer safe configuration gating for the API base address. If an existing feature-flag mechanism is reused, it must be limited to App.Desktop behavior and must not require server/shared contract changes.

Events:
No events are added in this docs-only PR.

The future S2-51 runtime should not add domain events or integration events. SignIn success should update only the existing in-memory desktop session boundary unless a later approved task expands event scope.

Offline behavior:
S2-51 SignIn enablement is online-only.

No offline queue, offline upload, offline SignIn expansion, or cached-credential login is approved.

If the control plane is unavailable, the UI-safe result must be a safe unavailable/error state with no secret leakage and no plaintext persistence.

Rollback:
Revert this docs-only task card and S2-51 handoff/prompt.

For the future runtime implementation, revert the future S2-51 runtime PR. Because future S2-51 must not change contracts, migrations, App.Api, deploy, or storage schema, rollback should be limited to App.Desktop and App.Desktop.Tests changes.
