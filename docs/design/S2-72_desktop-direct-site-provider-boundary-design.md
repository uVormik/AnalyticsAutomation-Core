# S2-72 Desktop Direct Site Provider Boundary Design

Status: design draft.

## Background

S2-71 probed the existing App.Api, WebsiteIntegration, VideoUpload, and shared contract surfaces.

Result: no approved direct-site provider configuration, upload request contract, upload response contract, endpoint/base-address, or media-byte transfer boundary was found.

Therefore real direct-site upload from App.Desktop remains blocked until an approved provider boundary exists.

## Non-negotiable architecture rules

App.Api remains the control plane.

Video bytes must not go through App.Api.

The desktop client uploads bytes directly to the approved site/provider endpoint.

App.Api stores receipts, sync state, duplicate registry, incidents, and audit state.

PreUploadCheck remains the gate before direct-site upload.

UploadReceipt remains the authoritative post-upload control-plane record.

## Boundary to approve before implementation

A future provider implementation must have an approved boundary with these parts:

1. Provider identity

- provider key
- provider display name
- provider capability set
- environment label if needed
- disabled/unavailable state semantics

2. Provider configuration

Required design decisions:

- where provider base address is configured
- whether config is environment variable, appsettings, encrypted local config, or server-provided control-plane metadata
- whether config is per tenant, per branch, or global
- whether provider config can change while the app is running
- how invalid/missing config is surfaced in the desktop UI
- how config is redacted in logs and diagnostics

3. Upload request contract

Required design decisions:

- target upload URL or route shape
- HTTP method
- required headers
- allowed auth scheme
- idempotency key usage
- external video id / storage key source of truth
- content type and size requirements
- checksum requirements
- timeout and retry rules
- cancellation behavior
- large-file streaming behavior
- what fields must never be logged

4. Upload response contract

Required design decisions:

- success response shape
- provider external video id semantics
- storage key semantics
- provider status values
- provider receipt/correlation id if any
- checksum echo if any
- failure response shape
- retryable vs non-retryable failure classification
- redaction rules for raw provider response

5. Security and token boundary

Required design decisions:

- whether provider upload uses a provider token, signed URL, temporary credential, or no credential
- who issues provider credentials
- credential lifetime
- whether credentials are generated by App.Api control plane
- whether credentials are single-use
- whether credentials are scoped to user/device/group/video
- how credentials are stored in App.Desktop memory
- how credentials are redacted
- whether provider credentials are ever persisted
- how auth failure is represented in UI

6. UploadReceipt linkage

A future real provider response must map to UploadReceipt without inventing fake success.

Required design decisions:

- how PreUploadCheckId is carried through
- how UserId, DeviceId, GroupNodeId are preserved
- how ExternalVideoId is sourced
- how StorageKey is sourced
- how SiteStatus is normalized
- how SizeBytes and ByteSha256 are verified
- how IdempotencyKey is generated and reused
- how UploadedAtUtc is selected
- what happens if direct-site upload succeeds but UploadReceipt fails
- what happens if UploadReceipt succeeds but later provider reconcile differs
- how duplicate/fraud incident flow is triggered after sync/reconcile

7. Offline behavior

Future implementation must explicitly define offline behavior.

Current expected default:

- real direct-site upload requires online control-plane pre-upload check
- offline mode cannot guarantee absolute duplicate prevention
- offline upload completion must not fabricate server receipt authority
- late sync/reconcile must be explicitly designed in a separate task if needed

8. Observability and redaction

Required rules:

- no password values
- no access token values
- no refresh token values
- no Authorization header values
- no provider credential values
- no signed URL query secrets
- no raw local file path
- no raw request body
- no raw response body
- no full byte hash unless explicitly approved
- no screenshots containing secrets

Allowed observability examples:

- provider key
- upload attempt correlation id
- safe status enum
- safe retry classification
- elapsed time
- size bucket
- redacted endpoint host only if approved

## Proposed App.Desktop shape

Implementation is deferred, but a future App.Desktop slice should likely keep:

- IDesktopDirectSiteUploadClient
- DisabledDesktopDirectSiteUploadClient
- provider unavailable UI state
- request preview without secrets
- fake/dev client only for debug visual smoke
- live provider client only when approved config and contract exist

A future HttpDesktopDirectSiteUploadClient must not be added until the provider contract is approved.

## Proposed App.Api / backend shape

No App.Api change is made in S2-72.

Future App.Api/backend work may be required only if approved:

- provider upload credential issue endpoint
- provider capability/config metadata endpoint
- direct-site provider policy endpoint
- receipt/reconcile support
- audit/event hooks

Any such change must be a separate task card and PR.

## NO-GO conditions

Do not implement real direct-site upload if any of these are true:

- provider base address is not approved
- upload request contract is not approved
- upload response contract is not approved
- auth/token boundary is not approved
- redaction rules are not approved
- UploadReceipt mapping is not approved
- retry/idempotency behavior is not approved
- security owner/platform owner has not approved
- implementation would send video bytes through App.Api

## Follow-up implementation sequence

Recommended sequence after S2-72 approval:

1. S2-73 provider config/options + disabled/live selection tests.
2. S2-74 provider request/response DTO contract if approved.
3. S2-75 desktop live provider client without real secrets in tests.
4. S2-76 UploadReceipt linkage after provider response.
5. S2-77 controlled live smoke with approved provider and redaction.

## Review checklist

Reviewer should confirm:

- design does not sneak in implementation
- App.Api remains control plane
- video bytes never go through App.Api
- fake/dev path remains isolated
- provider config is not invented without approval
- UploadReceipt authority remains server-side
- security/redaction rules are explicit
- next implementation slices are separated
